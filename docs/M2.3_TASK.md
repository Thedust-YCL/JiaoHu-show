## 2. 核心用户流程

### 2.1 主流程：BUILD → RUN → INSPECT → COMPARE → REBUILD

1. 用户进入 Agent Laboratory，在现有 Constructor 中选择当前配置作为 **A / Baseline**。
2. 用户将 A 复制为 **B / Variant**；可调整 Tools、Skills、Retrieval、Memory、Runtime、Guardrails 等配置，或选择已有本地配置。
3. 面板显示**差异摘要**，清楚列出哪些字段不同、哪些一致，以及是否存在配置错误。
4. 用户选择同一份本地研究任务、同一资料包版本、同一模拟场景和相同 seed。
5. A/B 先分别执行 M2.1 Preflight；若一侧不通过，禁止显示“双方成功完成”。可允许预览配置差异，但需显示阻断原因。
6. 通过预检后，调用**同一个 M2.2 引擎**分别运行 A 和 B，生成各自独立的 `runId`、配置快照、事件、报告结果。
7. 展示指标和运行路径的双栏对比；用户选择任一差异项，检查对应事件、分支依据和引用来源。
8. 用户切回 Constructor 修改 B，再次运行产生**新实验版本**，旧对比记录保持不变。
9. 用户保存实验档案或导出 Markdown 对比报告。

### 2.2 真实有效的差异示例

- A 禁用证据核验，B 启用证据核验：若场景包含冲突，B 可能出现额外核验步骤或明确的冲突解决过程；A 必须保留不确定性，不得伪造已验证结论。
- A 使用固定 Workflow，B 使用 Agent Loop：显示可解释的步骤选择差异，不能单靠改 UI 文案假装有差异。
- A 不允许某工具、B 允许该工具：如需该工具，一侧可出现权限拒绝/能力缺失，另一侧按规则继续；不要硬编码“B 一定赢”。
- 两侧配置完全相同：应允许出现语义等价的轨迹与结果，不能为了展示“对比价值”强造不同结果。

## 3. A/B 比较的数据模型

### 3.1 复用优先

先检查现有 `AgentConfiguration`、`RunRecord`、`ResearchReport` 和本地实验存储接口。新增类型只承载**配对与比较**，不复制底层业务对象。

参考形态（字段可依现有命名调整）：

```ts
type ComparisonExperiment = {
  schemaVersion: number;
  experimentId: string;
  title: string;
  note?: string;
  createdAt: string;
  updatedAt: string;
  baseline: { label: "A"; configSnapshot: AgentConfiguration; runId?: string };
  variant: { label: "B"; configSnapshot: AgentConfiguration; runId?: string };
  controls: {
    taskId: string;
    datasetId: string;
    datasetVersion: string;
    scenarioId: string;
    seed: string | number;
    approvalPolicyId?: string;
  };
  comparison?: ComparisonResult;
};
```

`ComparisonResult` 应引用双方运行 ID 与具体事件/证据 ID，而不是仅保存重复的 HTML 文本。比较用的指标、证据状态、成功/失败判定应是根据**已保存的不可变运行记录和版本化资料包**确定性计算的派生结果，可缓存但必须校验版本。

### 3.2 不可变快照与可复现性

- 运行后不得悄悄更新 A/B 的历史配置快照。
- 比较双方必须使用同一 task/datasetVersion/scenario/seed；如资料版本不同，只允许显示**非严格对比**警告，不得给出公平结论。
- 某些场景涉及用户 Approve/Reject：记录明确的审批输入序列或每侧对应的审批决策；不可将一次用户操作未记录地复用到另一侧。默认建议配对运行使用**相同的预设审批策略**，并显式展示每侧实际审批事件。
- 不使用墙钟时间、动画帧率或生成日期来决定业务分支；语义复现可以忽略 runId、创建时间等非决策元数据。
- 刷新、载入历史或复制实验不应篡改旧快照；复制应生成新的实验 ID，旧档案原样保留。
- 数据包升级后保留旧版本引用或明确报告不能精确复现；绝不能静默改用新资料后仍称“同条件复现”。

### 3.3 运行终态与缺失结果

- 支持 completed、failed、cancelled、step-limit、permission-denied、evidence-insufficient 等真实结果标签（以已有运行模型映射）。
- 某一侧未运行或预检失败时，对应指标标记 `N/A` 或 `未生成`，不能填 0 或“成功”。
- 对被取消或失败的运行，仍可比较可观察到的事件、终止原因与证据状态，但不可声称已有完整研究结论。
- 不同配置导致某个动作不存在时，不强行建立虚假的一对一事件匹配。

## 4. 指标比较引擎

### 4.1 只计算有来源的指标

至少支持以下维度，全部由既有事件、来源与报告产生：

| 维度 | 指标 | 数据依据 |
|---|---|---|
| 结果状态 | 完成 / 失败 / 证据不足 / 取消及终止原因 | RunRecord 终态、终止事件 |
| 执行路径 | 实际步骤数、关键步骤序列、分支数 | Execution Events |
| 工具使用 | 工具调用总数、各工具调用次数 | Tool-call events |
| 恢复策略 | 失败次数、重试次数、是否达到上限 | Failure/Retry events |
| 权限 | 请求/批准/拒绝次数 | Approval/Permission events |
| 证据覆盖 | 支持的关键结论条数 / 需要证据的关键结论条数 | M0.4 Evidence/Report |
| 引用有效性 | 能否从结论定位到有效的原始资料片段 | Citation mapping |
| 资料冲突 | 是否发现冲突、是否核验及核验结果 | Evidence events + metadata |
| 配置成本（教学） | 启用模块数、模拟步骤/调用开销 | Config snapshot + events |

**不得计算**虚构的实际 Token 消耗、真实费用、真实准确率、实际网络延迟或“智力指数”。如有规则化的演示代价分数，必须明确计算公式与“教学模拟估算”性质；默认不纳入 M2.3 P0 指标。

### 4.2 解释与追溯

- 每条指标有 `metricId`、定义、算法/统计口径、A/B 值、差值或差异状态、说明和可定位的源事件引用。
- 除非口径确实一致且可直接比较，否则显示“不可直接比较”或 N/A。
- 相同值应显示相同，不能强行给 B 贴“优化”标签。
- 证据覆盖不得以“报告字数更多”替代；引用存在也不等于引用支持论点。
- 允许用户从差值点进对应的执行事件、来源、报告段落，不仅显示纯数字。
- 效率与可靠性存在取舍：额外核验调用可能增加步骤，但改善证据支持度。不能机械用“步骤更少＝更好”或“Agent 模式＝更先进”。

## 5. 执行轨迹与分支可视化对比

### 5.1 比较模式

提供两个视角，共享 A/B 数据：

1. **Side-by-side**：左右两侧运行轨迹、报告状态和 Inspector，可独立滚动，并提供选择性联动定位。
2. **Difference View**：对齐可比的关键阶段（接收任务、检索、读取、核验、汇总等），突出新增、缺失、失败、重试、审批和不同结论。

基础对齐依据应是**结构化事件类型/stepKey/阶段与稳定来源引用**，而非仅凭数组下标或时间戳。对齐算法遇到重复步骤或不完整记录时应容许未匹配事件并解释理由，不能随意伪造成同一步。

### 5.2 Inspector 与时间轴

- 点击对比指标 → 定位关联侧的实际事件或报告证据。
- 点击 A 的某一步 → 可查看 B 是否存在可比较步骤；不存在时显示“未执行该步骤”。
- 展示事件输入/输出摘要、分支条件、角色、所用模块、资料 ID 与引用。
- 可暂停、按事件跳转与逐步浏览**已保存的轨迹**；回放速度只能影响视觉播放，不改变指标。
- 区分“过去真实生成的模拟执行事件”和“未选择的备用路径”。
- 避免错误使用“逐帧推理/模型思维可视化”等措辞；这里只展示本地执行规则与事件。

### 5.3 权限和人工选择

如双方出现待审批事件：

- 默认优先在各自独立 Run 中处理，双方审批输入均需明确记录。
- 配对自动演示可用**预定义审批脚本**，可复现并在 UI 可见。
- 不允许在 A 拒绝的动作被 B 未经授权自动执行，除非 B 的权限配置本来不同且明确解释。
- 审批差异应明确告知其对公平性的影响，不能混为 Runtime 模式差异。

## 6. 报告、证据和来源比对

1. 优先复用 M0.4 的报告结构、证据关系与 Citation System，不重新造第二套引用体系。
2. 并排展示两侧研究结论、证据清单、未核实项与局限说明。
3. 选择结论中的引用，应能定位到 **原始资料 → 具体片段 → 对应模拟执行事件 → 当前报告结论**。
4. 不能因为“更正公告发布日期更晚”就自动认定它必然权威；沿用已有 `supersedes`、来源元数据等证据规则。
5. 引用缺失、来源失效、证据不支持结论时，要清楚标记，而不是删除问题或自动补全不存在的数据。
6. 报告生成必须从双方各自的 RunResult 派生；更换配置后新报告属于新运行，不能覆盖旧运行中的引用结果。
7. 如果某一侧无法生成完整报告，应显示可解释的部分结果与原因，不伪造标准报告。

## 7. 3D AZ-CORE、2D System View 与知识体系联动

### 7.1 3D / 2D 同步约束

- **配置状态唯一来源**：M2.1 `AgentConfiguration`；**运行历史唯一来源**：M2.2 `RunRecord`；**比较数据**由上述两者派生。
- 切换 A/B 时，3D 核心显示选中侧的装配模块与配置状态，2D System View 和 Inspector 同步；界面必须明显标识当前是 A 还是 B。
- 对比页面若同时呈现两侧核心模型，可使用简化的静态/低资源预览，不强制同时渲染两套高开销完整 3D 场景。
- 在执行事件回放中，活动模块、请求连线和状态由**事件**驱动，不能靠动画决定业务执行结果。
- 同一模块选中后，提供相应的知识链接；选中事件可聚焦相关模块并标明当时配置快照。
- 切换 A/B 或视图时，不修改历史快照和事件顺序。

### 7.2 与 Atlas / Story / Journal 的关系

- 从模块、事件、指标说明可进入 M1 的正式概念详情，如 Workflow、Agent Loop、MCP、Skills、RAG、Memory、Tracing、Evals、Permissions。
- 返回实验室时保留当前实验、所选侧、活动对比项和滚动/事件位置（在合理范围内）。
- 知识正文不复制到实验室组件；使用 M1 统一内容接口。
- Knowledge Journal 只记录用户真实的学习事件；运行 A/B 实验不应自动等同于“已掌握”知识。
- 实验档案与学习进度、Journal、构建器配置在本地持久化层面保持隔离。

## 8. Experiment Archive：本地实验档案

### 8.1 最低能力

- 实验列表：名称、日期、A/B 配置摘要、研究任务、场景、运行状态、可复现标记。
- 新建实验、保存、打开、重命名、复制、删除；删除必须确认并显示范围。
- 保存一组 A/B 配置**不可变快照**、运行 ID、配对控制条件、比较指标版本与所需引用。
- 从档案打开原始 Run 与对比结果；不能依赖“当前编辑中的配置”重算历史以致结论变化。
- 从历史实验再次运行：创建新 Experiment/Run 记录或版本，不覆盖历史。
- 支持空状态和损坏档案的可理解恢复方式。

### 8.2 版本与容量

- 采用独立的 IndexedDB 或与现有应用一致的本地存储策略，避免把庞大事件 JSON 无限制写入 localStorage。
- 对 schemaVersion、datasetVersion、comparisonAlgorithmVersion 等做版本记录；升级需非破坏性迁移。
- 设定合理数量/容量上限，提供用户可见的清理方式；禁止静默删除所有历史实验。
- 因静态资料版本缺失而不能精确复现时，应标记“不可精确复现”，仍允许浏览旧的已保存摘要。
- 历史实验与当前配置、Journal、学习进度、其他 Run 相互独立；删除实验时对共享运行记录应有清晰引用策略，不误删其他引用者需要的数据。
- 不保存密码、Cookie、API Key 或不必要的完整用户文本。

## 9. 导出与分享边界

### 9.1 Markdown 导出（必须实现）

使用浏览器本地文件生成能力输出对比摘要，包括：

1. 实验名称、生成日期、`SIMULATION / 本地模拟` 声明。
2. A/B 配置的关键差异（字段、模块与权限）。
3. 任务/数据包版本/场景/seed/审批策略等控制条件。
4. 双方运行终态与比较指标定义、结果。
5. 关键不同分支及对应 Event ID。
6. 研究报告结论、证据来源 ID、未解决的冲突与限制。
7. 可复现性信息及不能直接比较的说明（如有）。

禁止导出虚构的真实搜索 URL、模型费用或不存在的来源。导出必须真正下载 Markdown 文件，不得仅显示“导出成功”提示。

### 9.2 JSON（可选，不阻塞 M2.3）

只有现有架构能够安全地序列化版本化实验快照并完成导入校验时才实现。不得把可选导入/分享扩张为公网托管、后端同步或上传接口。

- 继续遵守 `DESIGN_SYSTEM.md`，保留“黑曜虚空 + 精密终端 + 机械轨道 AZ-CORE 01”的视觉身份。
- A/B 侧有稳定的字母、标题、边框样式；不能只靠 Cyan/Amber 区分。
- 1440×900 优先兼顾中央可视面积、比较表与 Inspector。窄屏切换为 A/B 标签页或上下纵向比较，不把两列压成无法阅读的小字。
- 对比差异高亮克制、可解释；错误、警告和证据不足均需文字或图标提示。
- 支持键盘焦点、标签页导航、事件定位、回放控制和删除确认。
- 支持 `prefers-reduced-motion`；减少动效不影响对比结果或报告。
- WebGL 不可用时仍可查看 A/B 配置、运行指标、轨迹、证据与档案。
- 所有按钮真实可用；加载、无运行、单侧失败、无差异、数据失效等状态均有清晰 UI。
- 不新增毫无作用的控制台装饰按钮或虚构的评分/仪表数据。

## 11. 纯前端和安全红线

- 所有配对运行、比较、报告、存储与导出都在浏览器完成。
- 禁止 Flask、FastAPI、Express 后端、Serverless Functions、云端数据库、远程运行 API。
- 禁止真实 LLM、远程 Embedding、实时搜索、真实 MCP Server、第三方工具调用。
- 核心资料包、脚本、字体、模型等必要资源必须随静态构建发布；主动打开的外部技术参考链接不属于核心依赖。
- 不接受 API Key，不执行用户输入代码，避免 `eval` 和不必要的 HTML 注入。
- 不伪称模拟结论是实时研究结果、真实模型回答或真实安全认证。
- 不主动推送 GitHub、不部署上线、不做破坏性 Git 操作。

## 12. 推荐开发顺序

1. **Audit**：记录 M2.1、M2.2 和 M0.4 的真实接口、数据版本、兼容性缺陷与现有测试。
2. **Comparison Schema**：建立 Experiment/Pair Controls/Comparison Result 的最小版本化模型。
3. **Pair Runner**：复用 M2.2 Engine 运行 A、B，保证不可变快照、公平控制、独立 Run ID。
4. **Metrics**：从事件、报告和证据派生确定性指标，补齐 N/A/失败态规则。
5. **Trace Diff**：根据阶段/事件类型对齐轨迹，突出分支、重试、权限和来源差异。
6. **Report Provenance**：复用 M0.4 引用链，实现双侧结论与证据溯源。
7. **UI Integration**：完成 A/B 对比工作区、3D/2D 状态、Inspector、知识联动。
8. **Archive & Export**：本地存档管理、精确复现判定、Markdown 导出。
9. **Accessibility & Fallback**：键盘、窄屏、减少动态效果和 WebGL 降级。
10. **Verification**：执行 A01–A40、自动测试、类型检查、静态构建与 M0–M2.2 回归。

## 14. 自动测试最低范围

- A/B 选择、复制、差异摘要与编辑器状态独立。
- 配对条件不一致、数据集版本变化、审批策略未记录时的限制与警告。
- 不可变快照、不同 runId、旧报告不受当前编辑影响。
- 相同配置对比无虚假差异；不同配置真实影响已支持的执行规则。
- 完成、失败、取消、预检阻塞、一侧未运行时指标显示正确。
- 步骤、工具调用、重试、权限事件、冲突与证据覆盖的计算口径。
- 对重复事件、缺失步骤、额外重试的差异对齐容错。
- 报告每项引用映射到真实本地资料和实际执行事件；失效引用产生错误提示。
- 切换 A/B 时 3D/2D/Inspector 同步，动画暂停或跳过不改变结果。
- Atlas/知识详情跳转及返回上下文恢复。
- 实验档案保存/加载、复制、重命名、删除、坏记录恢复、数据版本迁移。
- 删除档案与配置、Journal、学习进度、共享 Run 之间的存储隔离。
- Markdown 导出内容与当前实验的真实指标一致，包含模拟声明、来源和版本信息。
- M0.1 电影开场和核心、M0.2 装配、M0.3 Atlas/Replay、M0.4 报告/引用回归。
- M1 六章、六 Lab、Story、Journal 的关键回归。
- M2.1 Schema/Preflight/本地配置，M2.2 各状态/分支/审批/终止/历史回归。
- GitHub Pages 子路径静态构建、网络依赖清单、无 WebGL 下功能和窄屏键盘操作。

## 15. 完工汇报格式

1. **仓库审计**：当前 M2.1/M2.2 真实现状、接口、可复用组件及阻断问题。
2. **变更文件**：比较模型、运行复用、指标算法、UI、档案、导出、测试分组。
3. **数据模型**：实验快照版本、配对控制条件、Run 关联及迁移说明。
4. **公平性报告**：相同条件的保证方式、审批输入如何处理、非严格比较条件。
5. **指标与溯源**：指标公式、事件来源、证据链与失败/缺失情况。
6. **A01–A40**：逐项 PASS/FAIL/BLOCKED/NOT RUN，附实际证据。
7. **自动测试与构建**：真实命令、运行结果、测试数量与失败项。
8. **M0–M2.2 回归**：关键流程验证与未通过项。
9. **遗留问题**：P0/P1/P2，说明哪些阻碍 M2 正式结束或进入 M3.1。
10. **架构纪律**：纯前端、无真实 AI/远程研究 API，Git 仅本地变更，未部署。

## 16. M2.3 / M2 完成定义

只有当下列条件全部满足，才可声明 **M2 · AGENT LABORATORY 完成**：

- 既有 Constructor 配置能驱动单侧及配对运行，A/B 复用 M2.2 同一引擎。
- 两侧运行有不可变配置快照，配对条件明确，失败与差异真实可解释。
- 关键指标来自真实模拟事件与证据，报告引用可以定位到资料与事件。
- 用户可以比较路径、工具调用、重试、审批和研究结果，不能以外观假装系统已比较。
- 3D、2D、Inspector、Atlas 和知识详情的关联准确，同侧状态不互相矛盾。
- 实验档案在浏览器本地保存、打开、复制、删除、重跑及 Markdown 导出可用。
- 旧配置、历史运行、学习进度和 Journal 不因新功能丢失。
- M0–M2.2 关键功能未退化，自动测试、类型检查、静态构建有真实证据。
- 生产功能仍是 **100% 纯前端、无后端、无真实 AI API**，没有偷偷引入远程依赖。

**本阶段通过后，M2 正式结束；下一阶段为 M3.1：全站视觉与多端体验完善。**
