## 2. 核心使用流程

`CONFIGURE → PREFLIGHT → RUN → INSPECT → SUMMARIZE → SAVE LOCALLY`

1.  用户在 M2.1 构建器中完成配置。
2.  Runtime 读取同一份 `AgentConfiguration`，运行预检。
3.  用户选择一个本地模拟研究任务和一个可控场景。
4.  用户启动运行，可逐步执行或连续运行。
5.  执行过程中，Runtime 根据配置、任务数据和场景规则产生事件。
6.  用户可以暂停、继续、取消、查看步骤详情，或在权限节点进行批准/拒绝。
7.  遇到可恢复错误时，系统按 `maxRetries`、`maxSteps` 和 Guardrails
    处理。
8.  运行结束后生成摘要和结构化事件轨迹。
9.  用户可在本地查看最近运行记录，或从同一配置和场景重新运行以复现结果。

运行历史是本地实验数据，不等同于 Knowledge
Journal，也不修改用户的知识学习状态。

## 3. 统一 Runtime 数据模型

先检查仓库是否已有等价类型；存在则扩展兼容，不要创建重复模型。

### 3.1 Run Record

运行记录至少应有：

-   `runId`：唯一 ID。
-   `configId` 与 `configSnapshot` 或等价的不可变配置快照。
-   `schemaVersion`：配置版本。
-   `scenarioId`：所用模拟任务/场景。
-   `seed`：用于确定性规则的种子或等价标识。
-   `status`：运行状态。
-   `startedAt`、`finishedAt`。
-   `events`：按序记录的运行事件。
-   `summary`：由事件轨迹计算的摘要。
-   `result`：结构化的最终结果与证据状态。

如果保存配置快照，必须清除不允许保存的秘密字段；当前架构本来就不得包含
API Key 等秘密。

### 3.2 Runtime Event

每条事件至少包含：

-   `eventId`：稳定且唯一。
-   `runId`。
-   `sequence`：单调递增的序号。
-   `timestamp` 或可复现的逻辑时间。
-   `type`：事件类型。
-   `stepId`（如适用）。
-   `moduleInstanceId`（如适用）。
-   `roleId`（如适用）。
-   `status`。
-   `inputSummary`、`outputSummary`：简明、可展示的摘要。
-   `reason`：本步骤为何发生、为何分支或为何终止。
-   `sourceIds`：引用的本地资料 ID（如适用）。
-   `errorCode`（如适用）。

不要为可复现性依赖真实墙钟时间排序。可使用独立的逻辑时间或稳定序号。用户界面可以额外显示本地格式化时间。

### 3.3 Step Result

每一步必须能表达：

-   执行的动作及对应模块。
-   开始、完成、跳过、失败、等待审批或被拒绝等状态。
-   使用的本地输入与来源。
-   产生的本地输出。
-   重试次数。
-   选中的分支及理由。
-   下一步或终止原因。

所有对象都必须可序列化，不能存储函数、DOM、WebGL 对象或运行时句柄。

## 4. 运行状态机

### 4.1 状态定义

-   `idle`：尚未建立可运行任务。
-   `ready`：预检通过，可以启动。
-   `running`：正在执行步骤。
-   `paused`：用户暂停，状态和事件轨迹保留。
-   `waiting_approval`：执行遇到需要审批的动作。
-   `completed`：正常达到终止条件。
-   `failed`：发生不可恢复错误或超过限制。
-   `cancelled`：用户主动取消。

### 4.2 状态转移要求

-   只有预检通过后才可从 `ready` 转入 `running`。
-   `running` 可以进入
    `paused`、`waiting_approval`、`completed`、`failed` 或 `cancelled`。
-   `paused` 可继续运行或取消；不得重置已完成步骤。
-   `waiting_approval` 在用户批准后继续，在拒绝后按 Guardrails
    规则结束或走安全分支。
-   `completed`、`failed`、`cancelled` 都是终态；重新执行必须创建新
    `runId`。
-   状态转移必须由 Runtime 逻辑管理，不能只由 UI 组件随意设置。
-   任何无效转移都要被阻止并可测试。

### 4.3 控制操作

-   `Run`：启动新运行。
-   `Step`：只执行下一个可执行步骤。
-   `Pause`：在安全的步骤边界暂停。
-   `Resume`：从暂停位置继续。
-   `Cancel`：取消当前运行并记录原因。
-   `Restart`：使用同一配置和场景创建新运行；不得覆盖原运行记录。
-   `Approve` / `Reject`：处理待审批动作。
-   `Reset View`：只重置临时视图状态，不删除运行记录。

连续运行与逐步运行必须使用同一引擎和同一规则，结果不可因控制方式不同而发生语义差异。

## 5. Runtime Engine：执行规则

### 5.1 基本研究任务

至少提供一个本地示例任务：**研究一项虚构校园活动并形成证据摘要**。

任务数据应包括：

-   研究目标。
-   一组本地虚构公告/资料。
-   至少一条可核验的来源元数据。
-   至少一个存在信息不完整或来源冲突的案例。
-   可由场景选择触发的工具失败、资料缺失、权限请求或证据不足条件。

明确标记为教学演示数据，不能让用户误认为是真实学校通知。

### 5.2 建议的基本执行步骤

实际步骤名称可沿用现有 UI，但至少体现下列逻辑：

1.  `TASK_INTAKE`：读取研究目标与约束。
2.  `PLAN`：根据 Workflow 或 Agent Loop 规则确定下一步。
3.  `RETRIEVE`：从本地静态资料中按已配置检索策略查找资料。
4.  `TOOL_CALL`：调用已启用的本地模拟工具。
5.  `EVIDENCE_CHECK`：检查证据是否存在、是否冲突、是否足以支持结论。
6.  `SYNTHESIZE`：按模板整理结果，不调用真实模型。
7.  `FINALIZE`：检查终止条件并输出结构化结果。

不得无条件执行全部步骤；步骤是否执行应受配置、前一步结果和场景规则影响。

### 5.3 配置驱动原则

运行引擎至少真实读取：

-   `executionMode`。
-   `maxSteps`。
-   `maxRetries`。
-   Model 行为预设（仅作为本地模拟规则输入）。
-   Instructions / `taskGoal`。
-   Context 与资料引用。
-   Tools 启用状态。
-   MCP 本地模拟能力目录。
-   Retrieval 设置。
-   Skills 选择。
-   Memory 模式与可用条目。
-   Guardrails 权限、审批和证据要求。

不得要求所有配置字段都必须对每个场景产生差异，但每个被声明为运行参数的字段必须有明确消费点、测试或文档。尚未被运行引擎使用的字段必须标为
`not_consumed_yet` 或提供等价的清晰状态，不能假装生效。

## 6. Workflow 与 Agent Loop 的真实差异

### 6.1 Workflow 模式

-   按预定义步骤图推进。
-   每个步骤具有明确的前置条件、输入与下一步规则。
-   发生可恢复失败时按配置决定重试；超过上限后进入明确的失败或降级路径。
-   不能因为某一步输出看起来完整就跳过必需的证据检查。
-   终止条件明确、可追踪。

### 6.2 Agent Loop 模式

-   每轮根据当前任务状态、证据状态、剩余步数和可用工具，确定下一动作。
-   允许根据资料不足、工具失败或证据冲突选择不同路径。
-   必须存在显式停止条件，不能无限循环。
-   每次决策记录
    `reason`，说明为什么继续检索、调用工具、请求审批、生成结果或停止。
-   不能仅仅把 Workflow 的步骤换一个名称就称为 Agent Loop。

### 6.3 教学解释

在运行面板中提供简洁的"为什么执行这一步"说明，帮助用户理解：

-   固定流程与基于状态选择动作的区别。
-   Agent Loop 不是无限循环。
-   计划不是结果保证。
-   工具调用成功不等于证据可信。
-   最终输出必须受到来源、权限和终止条件约束。

## 7. Branch Simulation：可控分支与故障场景

所有分支必须来自可理解的条件，不得随机制造故障。

### 7.1 最低场景集

至少提供以下场景开关或预设：

1.  `NORMAL_PATH`：本地资料齐全，工具正常。
2.  `MISSING_EVIDENCE`：关键资料缺失，需进一步检索或以证据不足结束。
3.  `TOOL_FAILURE_ONCE`：某次工具调用失败，允许在重试预算内恢复。
4.  `TOOL_FAILURE_EXHAUSTED`：工具持续失败，最终触发失败/降级。
5.  `CONFLICTING_SOURCES`：两条本地资料互相冲突，需说明冲突而非擅自选择。
6.  `PERMISSION_REQUIRED`：下一动作需要审批，运行进入
    `waiting_approval`。
7.  `PERMISSION_DENIED`：动作被拒绝，必须遵守权限策略。
8.  `STEP_LIMIT_REACHED`：达到 `maxSteps`，运行按定义终止。
9.  `UNTRUSTED_INSTRUCTION`：本地资料含有试图覆盖系统规则的恶意文本示例，需作为不可信数据处理。

这些场景应可由用户在运行前选择，或由任务数据中的确定性条件触发。必须说明场景是本地教学模拟。

### 7.2 分支图与轨迹

-   在执行轨迹中清晰标示分支点、选择条件、走过的路径与未选择的备选路径。
-   只将真实经过的分支标为已执行。
-   备选分支可以查看原因，但不得伪造其运行结果。
-   相同配置、场景和种子必须得到相同分支选择与结果。
-   如允许从头重跑，生成新的 run 记录，不覆盖原记录。
-   本阶段可支持"从头使用另一场景重跑"；复杂的从任意中间节点分叉和结果对比属于后续扩展，不得因此开发
    M2.3 全量对比系统。

## 8. Retry、恢复与终止

### 8.1 重试规则

-   仅可重试被明确标记为可恢复的错误。
-   重试次数不能超过配置中的 `maxRetries`。
-   每次重试必须产生独立事件，包含尝试次数、错误原因与结果。
-   权限拒绝不能被当作普通工具失败而自动重试。
-   输入校验错误不能通过重复执行解决。
-   超过重试上限时进入明确的失败、降级或证据不足路径。

### 8.2 步数限制

-   每次被定义为一次运行步骤的动作都要消耗 `maxSteps` 预算。
-   计数规则必须一致并写入文档。
-   达到上限后不得继续生成隐藏步骤。
-   结束摘要需说明是否因步数上限终止。

### 8.3 恢复语义

-   `Pause` / `Resume` 保留现有事件轨迹、已完成步骤与重试计数。
-   `Cancel` 记录取消事件与原因。
-   用户改变配置后不能在同一 run
    中静默改变配置；当前运行应使用启动时的不可变快照。
-   若配置被删除，已有运行记录仍须能展示快照和结果（前提是本地保存策略允许）；不得依赖实时配置对象才能显示历史。
-   页面刷新后的运行恢复行为必须明确：可恢复的暂停状态可以恢复，正在执行的运行不得在刷新后偷偷继续。

## 9. Permissions & Guardrails

### 9.1 运行时权限检查

每次受权限约束的工具动作执行前，必须读取本次运行的配置快照并进行校验。

-   允许：记录授权规则并执行本地模拟动作。
-   需审批：转入 `waiting_approval`，暂停后续步骤。
-   拒绝：记录拒绝原因并走安全分支。
-   无规则/未知权限：默认拒绝或要求审批，遵循最小权限原则。

### 9.2 审批交互

-   显示待审批动作、请求原因、所需权限、影响范围和可选操作。
-   用户可批准或拒绝；拒绝后不得继续执行被拒绝的动作。
-   不得将"批准"显示成真实系统权限授权；它只影响本地模拟。
-   重跑时重新按该次配置和场景判断审批，不继承旧 run
    的审批结果，除非现有产品规格明确要求。

### 9.3 Prompt Injection 场景

-   将恶意文本视为不可信资料内容，而不是可执行指令。
-   显示它试图要求系统做什么，以及为何不能覆盖更高优先级的规则。
-   记录 Guardrails 决策与事件。
-   不把安全演示夸大为真实生产级防护保证。

## 10. Multi-role Collaboration：多角色协作模拟

本阶段实现可解释的角色交接模拟，不调用多个真实模型，也不把多个角色包装成真实独立智能体。

### 10.1 最低角色

至少提供：

-   `Researcher`：检索与收集资料。
-   `Verifier`：检查来源、缺失信息和冲突。
-   `Synthesizer`：整理结论与限制说明。

角色定义来自本地静态配置，具有职责、可访问模块和输出结构。可复用 M1.3 中
Multi-Agent 的教学概念与相关 UI。

### 10.2 协作规则

-   每次角色交接生成事件，记录交出者、接收者、交接理由与产物引用。
-   角色只能使用配置允许的工具与资料。
-   `Verifier` 应能标记来源不足或冲突，不能自动把所有证据判定为可信。
-   `Synthesizer`
    必须遵守证据要求；资料不足时应输出不确定性或无法下结论的状态。
-   若某角色不可用或其依赖未启用，运行应显示明确的降级/失败原因。
-   不同角色的输出必须是可检查的结构化模拟产物，而不是只改变头像和标签。

### 10.3 单 Agent 与多角色流程

-   允许同一任务使用单流程模式或多角色交接模式（若配置/场景明确支持）。
-   在执行时间线中显示角色交接和产物引用。
-   多角色模式应消耗同一 `maxSteps` 预算，不能通过拆角色绕过上限。
-   本阶段不做多个 Agent 的并行调度系统；以可追踪的顺序交接为主。

------------------------------------------------------------------------

## 11. Execution Inspector：运行追踪与结果

### 11.1 主布局

沿用现有设计系统，建议包括：

-   运行状态与本地模拟标记。
-   步骤时间线/轨迹图。
-   当前步骤详情。
-   事件日志与错误面板。
-   分支路径与备选路径说明。
-   权限审批面板（仅在需要时出现）。
-   结果摘要与证据清单。

不要为了增加控制台感而堆叠没有数据来源的指标。

### 11.2 步骤详情

每一步展示：

-   动作名称和模块/角色。
-   状态与步骤序号。
-   简明输入/输出摘要。
-   引用的本地资料 ID 和来源元数据。
-   决策原因。
-   重试次数、失败信息或权限结果（如适用）。
-   下一步与终止条件。

### 11.3 结果摘要

至少包括：

-   运行最终状态。
-   执行步骤数、工具调用数、重试数。
-   实际经过的分支。
-   权限请求/批准/拒绝数量。
-   证据数量、来源冲突状态和证据充分性状态。
-   最终结论或明确的"证据不足，无法得出结论"。
-   终止原因。
-   配置快照、场景 ID 与种子信息。

摘要必须从事件轨迹计算，不得单独维护一份可与事件冲突的数字。

------------------------------------------------------------------------

## 12. 本地运行记录与可复现性

-   运行记录使用独立的本地存储命名空间，不与 Agent
    Configuration、Knowledge Journal、学习进度或用户资料混用。
-   只保存有限数量的最近运行记录；保留策略需文档化。
-   删除一条运行记录不影响配置或学习进度。
-   运行记录损坏时显示可理解的错误，并允许移除损坏条目；不得静默清空所有记录。
-   相同配置快照、场景 ID 和 seed
    产生相同的步骤顺序、分支决策和最终结果。
-   事件序号单调递增且无重复 ID。
-   若逻辑时间依赖时间戳，重跑时应使用确定性逻辑时钟或保证时间字段不影响决策。
-   不记录不必要的完整用户输入、敏感文本或秘密。
-   提供"重新运行"操作时，必须创建新 runId 并保留原始记录。
-   本阶段的本地运行摘要为 M2.3
    提供数据格式，但不开发完整的实验比较产品。

------------------------------------------------------------------------

## 13. 视觉、交互与无障碍

-   严格沿用 `DESIGN_SYSTEM.md` 与 AZ-CORE 01 的视觉语言。
-   运行状态变化应有清晰的文字、图标和视觉反馈，不只依赖颜色。
-   3D
    核心可以显示当前步骤、活动模块或状态变化，但运行逻辑不能依赖动画。
-   提供逐步执行和连续运行两种方式，二者共享同一引擎。
-   键盘可以启动/暂停/继续/取消、选择事件、处理审批与查看步骤详情。
-   支持 `prefers-reduced-motion`，关闭动画后仍可读懂时间线和状态。
-   窄屏下可将时间线与 Inspector
    改为标签页或上下布局；不能隐藏关键错误或审批。
-   WebGL 不可用时，运行、步骤检查、审批、结果摘要和历史记录仍可使用。
-   所有控件必须有真实行为；加载、空状态、失败和取消状态均有明确反馈。

------------------------------------------------------------------------

## 14. 纯前端与安全红线

1.  所有运行、分支、工具、权限和角色逻辑在浏览器本地执行。
2.  禁止业务后端、云端数据库、账号服务、Serverless API 和远程运行服务。
3.  禁止真实 LLM、Embedding、MCP Server、外部工具调用和运行时远程搜索。
4.  所有示例资料和工具数据随静态构建打包。
5.  运行记录必须清楚标记为本地模拟，不伪装成真实研究或真实 AI 输出。
6.  不执行用户提供的脚本；禁止 `eval` 或动态代码执行。
7.  不将本地演示中的"权限批准"描述为真实系统授权。
8.  不把模拟 Guardrails 描述为生产级安全保证。
9.  不主动推送、部署或执行破坏性 Git 操作。

## 15. 推荐实施顺序

1.  **Audit**：审计 M2.1 配置 schema、预检、模块目录和存储状态。
2.  **Runtime
    Core**：实现状态机、步骤模型、事件模型、终止条件和确定性执行。
3.  **Workflow / Agent Loop**：实现并测试两种执行策略的区别。
4.  **Scenario & Branches**：实现本地研究任务与九种基础场景/故障条件。
5.  **Retry / Permission**：实现重试上限、步数上限、审批和拒绝路径。
6.  **Multi-role**：实现 Researcher、Verifier、Synthesizer 的顺序交接。
7.  **Inspector UI**：接入时间线、步骤详情、分支路径、错误与摘要。
8.  **Controls**：实现逐步执行、连续运行、暂停、继续、取消和重新运行。
9.  **Persistence**：保存有限运行记录，确保配置快照与记录隔离。
10. **Regression**：执行 A01--A40、M0--M2.1
    回归、自动测试、类型检查与生产构建。

## 16. A01--A40 验收清单

  ID    验收项           通过条件
  ----- ---------------- --------------------------------------------------
  A01   仓库审计         记录 M2.1 实际状态与阻塞问题
  A02   配置来源         Runtime 读取 M2.1 的统一配置 schema
  A03   运行快照         启动后配置不可变，修改配置不改变当前运行
  A04   状态机           合法状态转移正确，无效转移被阻止
  A05   事件模型         事件有唯一 ID、单调序号和结构化字段
  A06   预检门槛         配置存在 error 时不能启动
  A07   Workflow         固定流程按前置条件与终止规则执行
  A08   Agent Loop       根据当前状态和证据选择下一动作
  A09   模式差异         两种模式具有可测试的规则差异
  A10   步骤控制         Step 只执行下一步，连续运行共用同一引擎
  A11   Pause/Resume     暂停与继续保留轨迹和计数
  A12   Cancel           取消有事件和原因，不继续执行后续步骤
  A13   Restart          创建新 runId，不覆盖旧记录
  A14   场景选择         至少九种场景/故障条件可被确定性触发
  A15   分支记录         真实路径、条件、原因和未选分支可区分
  A16   工具失败         失败事件与结果明确，未伪装成成功
  A17   重试上限         重试不超过配置的 maxRetries
  A18   步数上限         达到 maxSteps 后没有隐藏步骤
  A19   证据不足         不能在证据不足时伪造确定结论
  A20   来源冲突         冲突被呈现，结果保留不确定性
  A21   权限检查         每次受限动作执行前检查配置快照
  A22   审批状态         需审批时进入 waiting_approval 并暂停后续动作
  A23   拒绝路径         拒绝后不执行受限动作
  A24   Injection 场景   不可信资料不能覆盖系统规则，决策有记录
  A25   多角色交接       Researcher/Verifier/Synthesizer 交接有结构化事件
  A26   角色权限         角色不能使用未授权模块或工具
  A27   Inspector        步骤详情、输入/输出、理由与错误可查看
  A28   运行摘要         摘要由事件轨迹计算且字段一致
  A29   可复现性         相同配置、场景和 seed 得到相同决策结果
  A30   本地历史         运行记录可保存、查看、重跑与单条删除
  A31   存储隔离         运行记录不误删配置、Journal 或学习进度
  A32   损坏记录         损坏数据可控降级，不静默清空全部历史
  A33   知识关联         运行步骤可链接相关知识概念，不复制知识正文
  A34   响应式/无障碍    键盘、窄屏、焦点和减少动态效果可用
  A35   WebGL 降级       无 WebGL 时运行与 Inspector 仍可用
  A36   纯前端约束       无业务后端、真实 AI、远程 MCP/搜索请求
  A37   视觉回归         AZ-CORE 01 与 M0/M1 视觉成果保留
  A38   数据边界         运行快照、日志与摘要可序列化且不含秘密
  A39   自动测试/构建    实际运行并记录测试、类型检查、生产构建
  A40   全阶段回归       M0.1--M2.1 关键流程有真实验证，遗留项如实列出

`NOT RUN`，并附真实证据。截图不能替代运行逻辑测试；未运行的检查不得标记通过。

## 17. 自动化测试最低范围

-   状态机合法/非法转移、终态处理和取消行为。

-   键盘、窄屏、减少动态效果与 WebGL fallback。

## 18. 完成后的汇报格式

完成后必须输出：

1.  **审计摘要**：M2.1 的真实完成状态与阻塞问题。
2.  **Runtime 架构**：状态机、执行策略、事件模型和终止规则。

    字段已被运行引擎实际读取，哪些尚未消费。

6.  **多角色流程**：角色职责、交接事件与权限边界。
7.  **A01--A40 状态**：PASS / FAIL / BLOCKED / NOT RUN，并附证据。

9.  **回归结果**：M0--M2.1 关键流程的真实验证。

11. **技术纪律确认**：纯前端、无真实 AI、无后端、无远程 MCP/搜索；说明
    Git 是否仅有本地改动。

## 19. M2.2 完成定义

只有满足以下条件，才可声明 M2.2 完成：

-   Runtime 根据 M2.1 的真实配置运行，不存在第二套配置状态。
-   Workflow 与 Agent Loop 有明确且可测试的差异。
-   运行状态机、步骤事件、分支、重试、权限审批和终止规则正确。
-   多角色交接可追踪，角色权限与证据边界明确。
-   运行结果、事件轨迹与摘要一致，并可用同一配置、场景和 seed 复现。
-   本地运行历史可用，且与配置、Journal 和学习进度隔离。
-   M0--M2.1 的关键功能没有退化。
-   自动测试、类型检查、生产构建和纯前端检查有真实结果。
-   失败、阻塞和遗留问题如实列出。
